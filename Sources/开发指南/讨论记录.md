# v1.0.0 升级方案讨论记录

## 议题一：是否接入同一 app-server daemon

### 当前结论
app-server 是管理 session 的协议服务，但不是“每个应用必然一个服务”的固定架构。一个 app-server 进程可以管理多个 thread，并接受多个连接；不同 app-server 进程之间的运行状态默认不共享。

本机实测存在两类实例：

- 托管 daemon：通过 Unix socket 接入，可查询其管理的 loaded thread，并接收状态广播。
- 独立 stdio app-server：由桌面端或其他客户端作为子进程启动，运行状态只在该进程内维护；另一个独立 app-server 只能看到持久化记录，不能看到其 loaded 状态。

因此，“是否接入同一 daemon”的真正问题是：状态栏能否连接所有目标 Codex 客户端实际使用的 app-server 实例，或确认所有目标客户端统一使用同一个可连接 daemon。仅共享 `$CODEX_HOME` 不足以证明这一点。

### 待确认
1. Codex Desktop、CLI、IDE 在哪些场景使用托管 daemon，哪些场景自行启动 stdio app-server。
2. 是否存在稳定的官方连接方式，让状态栏发现并连接这些独立实例。
3. 若不能统一接入，是否接受只监控 daemon 覆盖范围，或保留其他来源。

### 议题一补充：仅管理 CLI 是否可行

当前结论需要限定范围：

- 对于**已经接入托管 daemon 的 CLI 会话**：app-server-only 在实时状态层面可行。已实测 CLI 会话 A 由 daemon 管理并返回 active；daemon 可广播新 thread、active/idle、waitingOnUserInput，并通过 thread/read 补查历史 turn。
- 对于**机器上所有可能的 CLI 调用**：尚未证明都统一接入该 daemon。若某种 CLI 启动方式自行生成 stdio app-server，仍会出现与 Codex 客户端相同的实例覆盖问题。

即使限定为 daemon 管理的 CLI，完全替代文件轮询仍需单独处理：断线补查、turn 成功/失败/中断区分、daemon 不可用、未读状态，以及现有用量/通知功能的字段映射。若产品范围仅为“CLI 的实时运行状态”，则当前证据支持 app-server-only；若要求保留现有全部功能并覆盖所有 CLI 启动方式，则仍不能直接宣布完全可行。

## 议题二：CLI 会话一键打开

本机 CLI 帮助确认支持：

```bash
codex resume <SESSION_ID>
```

也支持使用会话名称；`--all` 可取消当前目录筛选，`--include-non-interactive` 可把非交互会话加入选择范围。官方文档也说明可以使用 `/resume` 或运行 `codex resume` 恢复已保存讨论。

### 结论边界

- 状态栏可以用已知 thread/session ID 启动一个新的 CLI 交互入口，达到“一键打开该会话”的效果。
- 这通常是新建一个 CLI 客户端连接，不等于把原来已经运行的 Terminal 窗口切到前台。
- 对 active 会话调用 resume 会加入同一个会话的交互通道；此前测试表明恢复连接可以收到输入请求并回答，因此状态栏不得用 resume 作为无副作用的“聚焦”操作。
- 要真正聚焦原有 CLI 窗口，需要知道它由哪个终端应用启动，并使用终端应用自己的窗口激活能力；app-server 协议本身不提供“激活已有终端窗口”的接口。
- 对已完成或 idle 会话，一键执行 `codex resume <id>` 风险较低；对 active 或 waiting 会话，应在 UI 上区分“打开副本/加入会话”与“聚焦原窗口”。

### 用户明确的一键跳转需求

核心动作是**聚焦已经打开的 CLI 界面**，不是创建新终端或恢复会话：

1. CLI 已开启多个会话，用户当前位于 A。
2. 状态栏监测到 B 的任务完成，展示提示。
3. 用户点击提示或触发快捷操作，切换到 B 原来所在的终端窗口、标签页或分屏。

据此调整议题二：

- 默认跳转动作不得执行 `codex resume`、新建会话或打开另一个 CLI 入口。
- 必须维护 `thread ID → 终端应用 → 窗口/标签页/分屏标识` 的映射。
- app-server 提供任务状态与会话标识；聚焦动作需由终端应用的控制接口完成。此前协议实测没有获得可用于直接定位原终端界面的标识。
- 只把终端应用切到前台不满足需求；必须选择承载 B 的具体界面。
- 不自动向 B 发送输入、回答请求或打断任务。
- 验收场景应包含同窗口不同标签页、不同窗口、分屏，以及窗口关闭后的失效处理。

待用户确认实际终端应用后，验证该终端是否支持准确聚焦及如何建立会话映射；当前尚未确认端到端可行性。CLI user-agent 中出现 WarpTerminal 只能作为线索，不等同于用户确认。

## 议题二补充：现有完成通知的跳转实现

当前实现位于 `Sources/CodexBar/StatusBarController.swift` 和 `Sources/CodexBarCore/CodexBarPresentation.swift`：

1. `CodexNotificationTracker` 检测会话从未完成状态进入 `completedAt` 更新，生成 completed 事件；等待输入/授权也生成通知事件。
2. `sendNotifications(for:)` 创建 macOS `UNNotificationRequest`。
3. 通知的 `content.userInfo` 只保存 `sessionID`，正文仅显示项目目录名，不保存提示词或会话正文。
4. 用户点击通知后，`didReceive` 取出 `sessionID`，构造 `codex://threads/<sessionID>`，调用 `NSWorkspace.shared.open(url)`。
5. 菜单中的会话行点击也调用同一个 `openCodexThread`，使用相同的 `codex://threads/<sessionID>` deep link。
6. 项目自己的 `Info.plist` 没有注册 `codex` URL scheme；该 scheme 由 Codex 客户端处理。状态栏只负责发起打开请求。
7. `CodexBarPresentation.threadURL(for:)` 只为 `client == .app` 生成 threadURL；CLI/IDE 行在核心模型层没有 deep link。但通知点击处理只根据 sessionID 无条件尝试 `codex://threads/<id>`，失败后调用 `openCodex()`；这不构成 CLI 原终端窗口跳转。

### 对本次需求的直接结论

现有“点击通知跳转”验证的是 **Codex Desktop deep link**，不是 **CLI 原窗口定位**。它没有保存终端应用、窗口、标签页、分屏或进程信息，也没有调用 Terminal/Warp/iTerm 控制接口。因此现有实现不能直接满足“CLI 多会话完成后跳到 B 原来的 CLI 界面”。

## 议题二补充：CLI 跳转的产品价值与同类实现

调研结论：对同时运行多个 CLI agent 的用户，完成/等待通知后跳回具体终端 pane 是高价值能力；只激活终端应用或打开新 CLI 会话不足以解决多会话切换。

公开同类实现包括：

- `claude-tmux-hop`：通过 tmux pane 状态记录项目、任务和等待原因，通知点击后执行 Terminal App → 窗口/标签页 → tmux session/window/pane 的完整导航；README 明确支持 iTerm2、Terminal.app，以及多种终端的 pane 定位。
- `Claude Code Notifier Plus`：支持 CLI 和 VS Code，macOS 下通过 terminal-notifier 和辅助功能权限点击通知聚焦对应 CLI 终端或 VS Code 项目窗口。
- iTerm2 官方 Python API 提供窗口、tab、session 的 focus 事件和 ID；WezTerm 官方提供 window focus，以及 activate-tab/activate-pane 等 CLI 能力。

这些实现共同点不是从共享 session 日志反推位置，而是在 CLI/终端启动时或 hook 中保存 terminal/TTY/tmux pane 等上下文，再由通知点击时调用终端控制接口。

产品判断：若本项目的目标用户包含“同时运行多个 CLI 会话”，该功能应列为 CLI 体验的高优先级差异化能力；若只服务 Codex Desktop，则现有 codex:// deep link 已足够。

架构约束：仅靠 app-server 的 thread 状态不能得到终端窗口位置。需要额外的 CLI 侧关联机制、终端适配器或用户显式配置；应优先支持一种终端（例如 Warp 或 iTerm2）和一种会话容器（例如 tmux），验证映射可靠后再扩展。

## 议题四：app-server 监测的第一版边界

为了替代当前本地文件轮询，需要把“监测”拆成三个层次：

1. **连接与发现**：发现可连接的 app-server 实例，建立 Unix socket/stdio/WebSocket 连接，并检测断线。
2. **实时状态**：接收 thread、turn、item 和 status 事件，维护 active、idle、等待用户输入等运行状态。
3. **重连与校准**：断线重连后通过 `thread/read`、`thread/loaded/list` 等请求补齐当前状态，避免依赖断线期间的事件重放。

当前证据支持的覆盖矩阵：

| 会话来源 | 可否由状态栏直接接入 | 实时监测结论 |
| --- | --- | --- |
| CLI 使用托管 daemon | 可以，通过 Unix socket | 已验证可行 |
| Codex 客户端的独立 stdio app-server | 当前没有稳定发现/接入方式 | 共享文件只能看到持久化记录，不能得到运行时状态 |
| 其他自行启动的 app-server | 取决于其监听方式和连接暴露 | 需要单独发现或显式配置 |

建议第一版先定义为：**用 app-server 完成所有已接入托管 daemon 会话的实时监测，并移除这部分的文件轮询**。同时保留“独立 app-server 尚未覆盖”的明确状态，不把 `$CODEX_HOME` 中的历史记录误报为实时运行状态。

第一版必须具备的能力：

- 启动时连接 daemon，并读取当前 loaded thread 和必要的历史状态。
- 订阅/接收新 thread、status changed、turn completed、等待输入等事件。
- 断线后自动重连，并通过读取接口校准，而不是假设事件会自动补发。
- 将 `active → idle` 与 turn 的 `completed/interrupted` 区分开，避免把中断误报为成功完成。
- 对 `notLoaded` 会话显示“有持久化记录但当前未被此 daemon 管理”，不显示为实时 active/idle。
- 保留本地文件读取作为迁移期校验或未覆盖实例的降级来源，但不再作为已接入 daemon 会话的主状态源。

待确认的第一个产品决策：第一版是否接受“只对托管 daemon 覆盖的 CLI 会话实现 app-server-only”，而把 Codex 客户端独立 stdio 会话列为后续接入目标。

### 用户确认

用户确认接受该边界：第一版只实现托管 daemon 下 CLI 会话的 app-server-only 监测；Codex 客户端独立 stdio app-server 的接入列为后续目标。

因此，第一版的成功标准不再是覆盖 `$CODEX_HOME` 中所有会话，而是：对当前可连接 daemon 管理的 CLI 会话，状态栏不依赖文件轮询即可持续获得准确的实时状态，并在断线后恢复一致状态。

## 议题五：状态栏如何连接托管 daemon

本机验证到托管 daemon 通过 Unix socket 提供 app-server 接口，当前路径为：

```text
~/.codex/app-server-control/app-server-control.sock
```

本地 CLI 提供 `codex app-server daemon start/restart/stop/version` 等管理命令，但帮助信息没有提供“查询监听地址”的独立命令。因此，第一版需要把“连接已有 daemon”和“是否负责启动 daemon”分开。

建议方案：

- 状态栏优先连接约定的本地 Unix socket。
- 连接成功后发送初始化请求，并读取当前 loaded thread/状态。
- socket 不存在、连接拒绝或协议初始化失败时，显示监测不可用并进入重试，不自动停止用户任务。
- 第一版不主动执行 `daemon start/restart`，避免状态栏改变用户的 Codex 运行时生命周期。
- 将 socket 路径、协议版本和连接错误写入诊断信息，便于后续适配路径变化。

该方案的前提是：托管 daemon 的 socket 路径在目标版本中稳定，或未来能通过配置/官方发现机制取得。当前路径是本机实测值，尚未证明是跨版本、跨平台的公开稳定契约。

待确认的下一个问题：第一版是否只连接已经运行的 daemon；当 daemon 未运行时，状态栏是否只重试并提示，还是允许状态栏主动启动 daemon。

### 用户确认

用户确认：第一版只连接已经运行的 daemon。daemon 未运行、socket 不存在或连接失败时，状态栏只进行重试并提示，不主动启动、重启或停止 daemon。

该决策将 daemon 的生命周期控制权保留给 Codex CLI/系统管理逻辑，状态栏只作为观察者连接。

## 议题六：连接建立后的状态同步顺序

连接 daemon 后不能只依赖后续事件，因为连接建立前可能已经发生状态变化。因此建议采用固定顺序：

1. 建立 Unix socket 连接。
2. 完成 app-server 初始化和能力协商。
3. 获取当前 loaded thread 列表及其当前状态。
4. 对需要展示历史摘要的 thread 读取必要的持久化信息。
5. 注册事件监听，接收后续 thread/status/turn/item 事件。
6. 事件处理与初始快照合并，按 thread ID 去重。

这里需要区分两类数据：

- **运行时状态**：active、idle、waitingOnUserInput、当前 turn 等，以 app-server 返回为准。
- **展示元数据**：标题、项目路径、最近消息、完成时间等，可由 app-server 的 read 接口补齐；必要时在迁移期与文件读取结果对照。

待确认的下一个问题：状态栏启动或重连时，是否只展示 daemon 当前 loaded 的 thread，还是同时展示 `$CODEX_HOME` 中的历史 thread，并明确标记为未加载/离线。

### 用户确认

用户确认：第一版只展示 daemon 当前 loaded 且可实时监测的 thread，不展示 `$CODEX_HOME` 中未被 daemon 加载的历史会话。

因此，第一版的会话列表是运行时列表，而不是历史会话列表；daemon 返回的 `notLoaded` thread 不进入状态栏展示，也不触发实时通知。

## 议题七：实时事件到状态栏状态的映射

第一版需要把 app-server 的事件和状态收敛为少量稳定的产品状态：

| app-server 信息 | 状态栏含义 |
| --- | --- |
| `active` 且无等待标记 | 运行中 |
| `activeFlags` 包含 `waitingOnUserInput` | 等待用户输入 |
| turn 完成且状态为 `completed` | 已完成 |
| turn 完成且状态为 `interrupted` | 已中断 |
| `idle` 但没有新的完成事件 | 空闲/已加载 |
| 连接断开或校准失败 | 监测不可用，不改变任务最终状态 |

需要避免的误判：

- 不能把所有 `active → idle` 都当作成功完成。
- 不能把 daemon 连接断开当作任务完成或失败。
- `waitingOnUserInput` 应优先于普通 active 展示。
- 事件可能重复或乱序，状态更新必须按 thread/turn ID 幂等处理。

待确认的下一个问题：状态栏是否需要把“已中断”作为独立的可见状态和通知类型，还是与普通“已完成”共用展示。

### `interrupted` 的含义补充

`interrupted` 表示当前 turn 没有按正常完成路径结束，最明确的触发方式是客户端或用户主动发送 `turn/interrupt`，例如 CLI 中按停止/Ctrl-C，或上层客户端点击停止。app-server 会为该 turn 发出 `turn/completed`，但其状态为 `interrupted`。

以下情况不能直接等同于 `interrupted`：

- 状态栏与 daemon 的连接断开：已实测 turn 可以继续在 daemon 中运行，连接恢复后再读取结果。
- 单个工具执行失败、权限拒绝或模型返回错误：通常应根据 item/turn 的错误信息单独表示，不要统一标记为用户中断。
- 只有 `active → idle` 而没有对应的 turn 完成事件：只能标记为需要校准/未知，不能推断成功或中断。

daemon 重启、客户端崩溃或异常退出可能导致未收到正常终态事件，属于“异常结束/未知”场景；第一版应通过重连后的读取结果确认，无法确认时不要伪造 `interrupted`。

### 用户确认

用户确认保留三种不同结果：已完成、已中断、异常结束/状态未知。

## 议题八：监测连接是否订阅完整 thread 事件

测试表明，app-server 存在两种不同的观察方式：

- 未恢复 thread 的连接可以接收新 thread、状态变化等全局级通知。
- 要接收某个 thread 的完整 `turn/*`、`item/*` 事件，通常需要执行 `thread/resume` 建立订阅。

`thread/resume` 不应被当作纯读取操作：测试中第二个连接恢复 thread 后，能够收到并处理输入请求，因此可能参与会话交互。

建议第一版采用“观察者连接”：

1. 连接 daemon 并接收全局 thread/status/turn 完成类事件。
2. 不主动对用户 thread 执行 `thread/resume`，不订阅完整 item 流。
3. 收到状态变化或完成事件后，用 `thread/read` 补充当前状态和必要摘要。
4. 只有未来明确需要逐项进度或实时文本流时，才单独设计可控的订阅机制。

这样可以完成菜单状态、完成通知和等待输入监测，同时避免状态栏意外成为 thread 的交互参与者。

待确认的下一个问题：第一版是否采用上述“只观察全局状态事件，不 resume thread”的连接策略。

### 用户确认

用户确认第一版采用观察者连接：不主动 `thread/resume` 用户会话，只接收全局状态事件，需要详情时使用 `thread/read`。

## 议题九：等待输入、权限请求与完成通知

目前已经确认 app-server 可以通过状态返回 `activeFlags: ["waitingOnUserInput"]`，因此第一版可以可靠识别“等待用户输入”。这与普通 active 不同，也不应等到 idle 后再处理。

需要区分三类需要用户注意的情况：

1. **等待用户输入**：任务暂停，等待用户继续提供信息。
2. **等待权限/审批**：任务可能暂停等待授权；当前观察者连接只读到了状态级能力，尚未证明不 resume 的连接能够取得完整审批请求内容。
3. **任务终态**：completed、interrupted、异常结束/未知。

建议第一版通知策略：

- 对等待用户输入发送通知，并在菜单中显示等待状态。
- 对已完成发送通知，沿用现有去重逻辑，但状态来源改为 app-server。
- 对已中断和异常结束先在菜单中显示，不默认发送通知，避免用户主动停止或连接异常造成通知噪音；是否通知可后续单独调整。
- 权限/审批请求在协议观察能力确认前，不承诺显示具体请求内容；至少保留“需要处理”的状态标记，避免误报为普通运行中。

待确认的下一个问题：第一版是否只对“等待用户输入”和“已完成”发送系统通知，已中断/异常结束仅在菜单中展示。

### 用户确认

用户确认第一版只对“等待用户输入”和“已完成”发送系统通知；已中断和异常结束/未知只在菜单中展示。

## 议题十：重连、补偿与通知去重

app-server 不保证客户端断线期间的历史事件会在重连后自动重放，因此状态栏必须把事件接收和状态校准结合起来：

- 连接断开时，将监测状态标记为“监测不可用”，但保留最近一次已知的 thread 状态。
- 重连成功后重新获取 loaded thread 和当前状态。
- 对仍处于 active 的 thread，继续观察后续事件。
- 对重连期间已经完成或进入等待输入的 thread，根据校准结果补发一次通知。
- 对已处理过的状态建立去重键，至少包含 `threadId + turnId + 事件类型/终态`。
- 同一 completed 或 waiting 状态重复收到时不重复通知。
- 如果重连后只能确认 thread 当前 idle，但没有对应 turn 终态，则不补发“已完成”通知，避免误报。

建议把以下信息作为状态栏本地运行时状态保存，而不是写回 Codex 会话数据：

- 最近一次成功连接时间。
- 每个 thread 最近已处理的 turn ID 和通知状态。
- 最近一次校准时间及失败原因。
- daemon 当前不可用的原因。

这些数据用于保证状态栏自身重启或连接抖动后的幂等行为，不改变 app-server 或 `$CODEX_HOME` 中的会话记录。

待确认的下一个问题：状态栏自身重启后，是否需要为重启前已经完成但尚未通知的 turn 补发通知，还是只处理重启后新产生的事件。

### 用户确认

用户确认：状态栏自身重启或断线重连后，需要补发离线期间已经完成、但状态栏尚未处理的 turn 通知；如果等待输入已经被用户回复并进入后续 turn，则不补发旧的等待通知。

## 议题十一：通知处理记录的持久化

要支持上述补发，状态栏需要维护自己的通知处理记录，不能只依赖内存：

- 记录每个 `threadId + turnId + 通知类型` 是否已经处理。
- 发送通知与写入处理记录需要设计为幂等流程，允许极端情况下重复一次，但不能持续重复。
- 重连校准时，只对已确认存在且未记录为已处理的 completed 或 waiting 状态补发。
- 首次安装或没有历史记录时，不应把所有旧的已完成 turn 当成新通知；需要建立初始基线，只追踪基线之后的新状态。
- 状态栏自身重启前已经成功记录的通知不重复发送。
- 记录只属于状态栏，不修改 Codex 会话文件或 app-server 数据。

建议第一版使用一个轻量本地状态文件或 UserDefaults 保存通知游标/去重键，并提供清理策略，避免无限增长。

待确认的下一个问题：首次启用 app-server 监测时，是否建立当前状态基线，不补发启用前已经完成的历史 turn。

### 用户确认

用户确认：首次启用 app-server 监测时建立当前状态基线，不补发启用前已经完成的历史 turn；只处理基线之后产生的新完成和等待输入状态。

## 议题十二：通知记录的保存形式与生命周期

通知去重和首次基线需要跨状态栏重启保存。第一版可选择：

- **UserDefaults**：实现简单，适合保存少量游标、最近 turn 和版本标记；不适合无限保存所有历史通知。
- **独立轻量状态文件/数据库**：适合保存多个 thread 的去重键和诊断信息，但需要定义格式、并发写入和清理策略。

建议第一版采用独立的状态记录结构，至少包含：

- 监测方案版本。
- 首次基线时间。
- 最近成功校准时间。
- 每个 thread 最近观察到的 turn ID、状态和通知处理标记。
- 已处理记录的保留时间或数量上限。

记录应与 Codex 的 session 文件分离，写入采用原子替换，损坏时可以丢弃并重新建立基线，不能阻塞实时监测。

清理策略建议保留最近一段时间或最近固定数量的已处理记录；仍处于 active/waiting 的 thread 不得因清理被遗忘。

待确认的下一个问题：第一版是否接受使用独立本地状态文件保存 app-server 监测游标和通知去重信息，而不是继续扩展现有 Codex session 文件读取逻辑。
